# 看板是视图，不是容器

首页引入看板（四象限、长期池）。我们决定：看板是一条**保存的分组规则**——把同一份任务按规则投影成列，任务不归属于任何看板或列，`Task` 上不存在 `boardId`/`column` 字段。

理由有三：其一，同一个任务必须能同时出现在四象限、长期池和它的项目页里——"一个任务放进哪个看板"这个问题本身就是错的。其二，四象限的本质是"重要×紧急"的规则分组，格子的成员资格由任务字段决定，而不是由用户摆放决定；用容器模型反而要回答"规则与摆放冲突时听谁的"。其三，现有架构已经是视图模型：`lib/tasks.ts` 的查询助手 + `misc.taskOrder` 按 viewKey 存手动顺序，看板只是多了几个 viewKey（`quadrant:<cell>`）和规则函数，零迁移。

## Considered Options

- **Trello 式容器**：被否决。任务要长归属字段、要写迁移、要回答"能否属于两个看板"；与项目/标签/今日等既有视图叠加后，同一任务会有两套互相矛盾的位置语义。
- **容器为主、规则为辅的混合**：被否决。两种心智模型并存，用户要分辨"哪些格子拖进去算数、哪些会自动流走"。

## Consequences

- 跨格拖拽必须翻译成对任务字段的改写：纵轴 = 切换 `isImportant`，横轴 = 修改 `dueDay`（见 ADR-0006）。不存在"放进某格"的存储。
- 格内手动排序沿用 `order:set`，viewKey 为 `quadrant:<cellKey>`；规则变化（如改阈值）可能让任务换格，手动顺序只对仍留在格内的任务有意义。
- 未来新增看板 = 新增一个规则函数 + 一个 viewKey，不动数据模型；预置看板与用户自建看板在表达力上没有差别。
