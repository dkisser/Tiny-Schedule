# 重要是任务的字段，不是系统标签

四象限看板需要一个"重要"标记。数据层其实早已预播种了两个隐藏系统标签 `EM_IMPORTANT` / `EM_URGENT`（为象限预留，但被所有标签 UI 过滤、无任何视图读取）。我们决定：`Task` 增加 `isImportant: boolean` 真字段，迁移把旧数据里的 `EM_IMPORTANT` 折叠进该字段，并把 `EM_IMPORTANT` 与 `EM_URGENT` 两个系统标签连同播种一并删除。"紧急"则根本不作为存储属性——它由 `dueDay` 派生（`dueDay ≤ 今天 + urgencyThresholdDays`，阈值默认 2，设置页可配）。

这是延续 `migrateRemoveTodayTag` 确立的方向：系统标签是魔法，真字段才是领域。标签是用户可见、可增删的分类机制，而"重要/紧急"是象限的坐标轴，语义固定、由产品定义，不该出现在用户的标签列表里被改名或误删。紧急选择派生而非存储，是因为手动维护的紧急标记必然腐烂：一个"重要不紧急"的长期任务随着截止临近应当**自动**滑进"重要紧急"，这正是"长期任务有人跟"的诉求本身，不能依赖用户记得去翻牌。

## Considered Options

- **启用休眠的 EM 系统标签**：被否决。零迁移，但延续魔法标签路线——正是 TODAY 标签迁移要消除的东西；且所有标签 UI（侧栏、选择器、新建对话框）要永远记得过滤它们。
- **重要、紧急都做存储字段**：被否决。紧急与 dueDay 会成为双源真相：改了截止日期却忘了摘紧急标记，象限就开始说谎。
- **紧急存字段、dueDay 只作提醒**：被否决。同样双源，且"截止临近自动变紧急"这一核心行为会丢失。

## Consequences

- 删除 `EM_URGENT` 意味着（理论上）打过该标签的数据丢失这一信息。可接受：该标签从未有任何 UI 入口，实际不可能被用户打上。
- 四象限看板里横向拖拽任务的语义是**改写 dueDay**（拖入紧急列=今天，拖入不紧急列=阈值外第一天），因为"紧急"没有可写的存储字段。这是有意为之的"拖拽即改期"。
- 启动迁移对每个数据集只跑一次；同一折叠函数也接入备份导入的合并路径，防止旧备份把已删的系统标签复活。`isImportant` 本身经 zod `.default(false)` 回填，无需迁移。
