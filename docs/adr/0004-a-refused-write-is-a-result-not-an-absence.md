# 被拒绝的写入是一种模式，不是一次操作的结果

ADR-0003 确立了"领域不变量在主进程强制"。本 ADR 处理它没覆盖到的一面：**当强制点自己拒绝执行时，这件事必须让用户看见。**

它最初的版本把拒绝当作每次操作的返回值逐通道传播；那份实现没有收敛，三轮 review 各在它自己上一轮的修复里找出新缺陷。改动的不是细节，是**拒绝被放在哪一层**。

## 背景：一个事实，走了三条路

`DataStore` 在 `data.json` 不可解析时会拒绝写入，以免用降级缓存覆盖用户唯一的好副本。PR #18 给 `update()` 加了 `persisted: boolean`，让这个拒绝可见——但只走了一条路：`WRITE_REFUSED` 只存在于 `TimingStopResult` 上，其余二十余条写通道仍返回裸 `AppData`，渲染进程只有三处各自写了 `toast.error`，`TimerPort` 与 `syncTimer` 的返回形状还不一致，于是自动暂停被拒时发出的 payload 与真实丢弃逐字节相同。

三轮 code review 反复在这几处发现新问题。这不是"不够小心"，而是**抽象放错了层**。

## 决定

### 拒绝是一种模式，不是一次操作的结果

第一性原理上，`data.json` 解析失败是应用**所处的状态**，与哪条通道、哪个任务、用户做了什么无关，持续到用户修好文件为止。把它当作每次写入的返回值，就必须逐通道传播；而每条新通道都多一个"要记得判断"的地方，漏掉是默认结果——漏掉还不会报错：它类型正确、测试全绿，只是让用户看着保存成功然后丢掉数据。

所以：

**`Ipc.storeWritable` 推送 store 的读写模式。** `DataStore.onModeChanged` 在 latch 翻转时通知（进入只读、文件被修复、损坏文件被删除三条路径），订阅时立即上报当前状态，避免"启动时已经 latch、订阅发生在之后"这种漏报。渲染进程据此显示 `StoreUnreadableBanner`——常驻、不自动消失、写出原因。

一次信号覆盖全部通道，包括十处 `void` 防抖提交（它们根本没人检查返回值）。这也顺带消灭了按次 toast：打二十个字弹二十次的那种。

### 只有控制流通道携带内联答案

仍需逐次回答的，只有一类：**返回值被当作控制流**的通道——调用方用它决定弹窗关不关、要不要跳转、TimerBar 动不动。从二十余条缩到五条：

`timingStop`、`taskUpsert`（完成路径）、想法/跟进命令集、`projectCreate`。

`timingStop` 有三条分支而不是两条，因为它有一个别的通道没有的情况：领域拒绝里
**主进程确实丢弃了计时并落库了**（任务已完成或已删除），渲染进程必须拿到那份
数据集才能收敛，否则会一直显示着一次结算根本没动过的旧 timeSpent。所以带 `data`
的拒绝与不带 `data` 的 `WRITE_REFUSED` 是分开的——按"有没有东西发生变化"划分，
而不是塞一个独立的 `persisted` 布尔让调用方判两件事。

判别式把"成功"和"落盘"合成一个真相：

```ts
type WriteOutcome =
  | { ok: true; data: AppData }
  | { ok: false; error: 'WRITE_REFUSED' };
```

`{ ok: true }` 蕴含已落盘，被拒时结果与既有领域拒绝**同构**。所以 `UpgradeIdeaDialog`、`CloseIdeaDialog` 等八处调用点原有的 `if (!result.ok)` 一行都不用改，也不存在"ok 为真但其实没存下来"的组合。

其余写通道返回裸 `AppData`：它们的结果只用来刷新界面，判据是"这个应用现在还在保存吗"，而那是一个全局状态。

### 诚实地说：类型系统给不了强制力

判别联合摆在那里，不检查也能编译、也能过测试。本 ADR 能保证的是把需要检查的通道从二十余条缩到五条，且每处检查都紧挨着一个**本来就存在**的分支——所以 review 看得见。它不能替代 review，也不假装能。

## Considered Options

- **给所有写通道加 `persisted`**：被否决。这就是 PR #22 第一版的做法，三轮 review 证明它不收敛。
- **让 `DataStore.update()` 直接 throw**：被否决。数据不可读是运行期的持久状态，不是异常；throw 只是把"记得判断"换成"记得 catch"。
- **拒绝时弹 toast，并加 latch 防重复**：被否决。latch 是"没有全局状态"的补丁——既然有状态可订阅，就不该用它。
- **降级数据集照常采纳**：被否决。`data.json` 损坏且无备份时主进程持有 `emptyAppData()`，采纳它会让整个库从界面上消失，而提示说的是"保存失败"。不过被拒时 store 的缓存根本没变，所以采纳本就是空操作——问题只在于不必要地保留这条路径。
- **引入独立的"只读模式"UI 状态**：即本决定。横幅而非 toast，因为它要持续到用户修好文件，而不是到下一次写入。
- **`timerChanged` 载荷改为判别联合**：单列一个 PR（#20）。它碰线格式，独立出来便于回滚。

## Consequences

- 新增写通道时**没有"要不要判断 persisted"这个自由度**了——状态通道返回裸数据（没什么可判断），控制流通道的拒绝由 `asCommand` 统一映射（不判断就编译不过）。
- 被拒的防抖编辑不回滚本地状态：把用户正在输入的标题弹回去更糟，而横幅已经说明"没存上"。拖拽排序同理。代价是本地状态可能与磁盘短暂不一致，直到该字段下次编辑。
- `countRecords`（备份轮转守卫）仍漏 `misc.chatSessions`，且是"记录数"这个代理指标。**本 ADR 不解决它**——那是备份保留策略（代际 vs 内容比较）的独立决定，见 #21。
