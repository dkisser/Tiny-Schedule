# 定时任务：权限默认全开，但能力收进网关通道

定时任务（ScheduledTask）到点驱动 LLM Agent 执行一段 prompt。Agent 的工具（runCommand / httpRequest / writeFile / readFile）能碰应用沙盒之外的世界：任意 shell 命令、任意目录、任意 host。本 ADR 记录它的权限模型：**不做逐任务授权声明，全部工具默认开放**——以及这个决定之下仍然保留的网关通道。

## 为什么不授权

CLI 式权限（Claude Code 的"执行目录 + 命令授权"）之所以成立，是因为命令在执行前已知，授权是一次性的、精确的。LLM Agent 不满足这个前提：模型在运行时才会决定调哪个工具、带什么参数，创建任务的人无法预知。声明清单只能靠"跑一次 → 看拒绝 → 补授权"事后凑齐——评估后认为这对无人值守的定时场景是持续摩擦而非一次性成本，故采纳默认全开。运行时弹窗授权同样被否决：无人值守意味着人不在场，弹窗即任务卡死。

这是本地优先的单用户应用，prompt 由用户本人编写，威胁模型里没有恶意用户。**被明确接受的风险**是"无人值守 + 模型出错"：幻觉出的破坏性命令、或 prompt 处理的数据里夹带注入文本，在全开模式下没有运行时防线。对策是审计兜底（见 Consequences），以及用户只对自己写得清楚的 prompt 开启定时。

## 但仍收进网关

现状是 renderer 碰不到外部世界：无 shell 插件、fs 收窄到应用数据目录、http 只放行 3 个 host。要支持上述工具，必须新增四个通用 Rust 命令：`exec` / `http_request` / `write_file` / `read_file`，capability 只暴露这四个入口。它们延续 ADR-0005 的薄壳原则（sse.rs 是先例），但"薄"不等于"散"——**每个命令收口为单一入口函数，请求始终带 taskId / runId 上下文**。现在入口直通执行、不做任何校验；收口是未来策略的挂载点：哪天要加回白名单或安全拦截，是在四个收口函数里加检查，而不是改架构。

拦截分两层：

- **TS 工具层拦截器（现在就建）**。对 Agent 而言，注册进 pi-agent-core 的工具是它对世界的全部接口（模型没有别的 invoke 通道），TS 拦截即完全中介。审计是这个拦截器的第一个住户：每次工具调用（工具、参数、cwd、host、结果、耗时）完整写入运行记录。这层管**记录与体验**：审计、计时、错误规整、超长输出截断。
- **Rust 收口（留钩子）**。强制类校验未来必须下沉到这里，不能只留在 TS——TS 拦截挡不住 webview 自身被注入（XSS、被污染的依赖、devtools 直接 invoke）。格局是：TS 管审计与体验，Rust 管强制；现在只有前者。

## Considered Options

- **声明时授权（能力清单 + 越界拒绝 + 拒绝记录一键补授权）**：被否决。对 LLM Agent 声明不成立（见上）；曾设计"从拒绝记录学习授权"的调试闭环来缓解，仍判定为持续摩擦。
- **tauri-plugin-shell 静态 scope**：被否决。scope 是构建时静态配置，用户的命令集运行时才知道，打包后无法扩展。
- **运行时弹窗授权**：被否决。与无人值守场景正面冲突。
- **Rust 裸 exec、不收口**：被否决。一个 `invoke("exec", 任意字符串)` 直通 shell，未来加任何策略都要改架构；收口的当期成本几乎为零。

## Consequences

- **审计是底线**：全开模式下运行记录是唯一的追溯手段，工具调用级日志不是可选项。
- 加回受限模式的路径已铺好：授权清单存 data.json，Rust 收口读它校验，TS 只负责把拒绝渲染进运行记录。本 ADR 不堵死这个回头路。
- 执行目录（cwd）保留为定时任务字段，但角色是执行上下文，不是权限边界。
- 四个网关命令是 capability 层唯一的越界开口，review 新增 capability 时应以"不绕过网关"为准绳。
