# 完成任务即结束该任务的计时

任务完成（`isDone: true`）会同时结束挂在它身上的计时：按用户点下"完成"的那一刻结算并清空，再把任务标记为已做完——这是一个动作，用户不需要先手动停止计时。之所以要动领域层：完成路径原先只写 `isDone`/`doneAt`，而进行中的计时是**全局单例**、独立存放在 timer store 里、仅通过 `taskId` 关联任务，两侧没有任何交叉，于是任务显示为已做完、计时却继续跑，时间被记到一个已做完的任务上。原因是结构性的而非遗漏：任务字段的任何改动都不可能影响那个单例，grep 也确认 timer 相关代码从不读 `isDone`，更没有任何 watcher 监听任务完成。

规则的执行点是**写任务的每一次落盘**（`upsertTaskWithTiming`），而不是某个 UI 入口。任何把任务从"未做完"翻成"已做完"的写入都会顺带结束它的计时，因此卡片勾选框、子任务勾选框、日后出现的快捷键或 agent 工具都不可能绕过它。任务与计时器在同一次不可变转换中一起移动，崩溃无法把它们留在不一致的中间态。

## Considered Options

- **只改完成那一处点击处理**：被否决。"完成"是会不断长出新入口的动作（快捷键、拖拽完成、子任务、批量完成），规则写在 UI 里，下一个入口就会重犯；主进程还有一条自己的结算路径（退出时 `settleActiveTimer`），共享领域动作才能让两条路径说同一种话。
- **在渲染进程分两次写（先写已结算的任务，再清计时器）**：被否决。这是本 ADR 初版的设计，代码审查发现它有一个可复现的重复计费缺陷。这两次写之间的任何中断——包括主线程上完整数据集重写的那段时间——都会留下"任务已做完且已结算，而 `activeTimer` 仍指向它"的盘面状态，而恢复路径无法分辨这是"修复前的旧数据、时间确实没记过"还是"本次写入被中断、时间已经记过了"，猜错就重复计费（实测 90 秒记成 180 秒，并多出一条逐字节相同的时间记录）。改为主进程一次 `store.update` 同时落盘后，这个窗口根本不存在。
- **新增一个专用的 `task:complete` IPC 通道**：被否决。把不变量放进既有的 `task:upsert` 即可，同样是单次原子落盘，还顺带堵住了"直接用 `taskUpsert` 写 `isDone`"这个后门，且不必改动 IPC 契约、preload 与 `check:ipc` 校验面。
- **完成只自动暂停、不清空**：被否决。会留下一个指向已做完任务的暂停计时器，它仍占着全局单例、退出时仍会被结算——把同一个 bug 变成静态版本，比现在更难发现。
- **禁止完成（必须先停止计时）**：被否决。等于把"先结束后完成"这个两步仪式制度化，而它要解决的歧义并不存在——完成动作本身已经唯一地决定了结束时刻。
- **静默结算，不询问**：被否决。会让"完成"在无反馈的情况下改写工时，用户不知道记了多少。改为弹确认框，并显示将被记入的时长；番茄钟半途时额外提示已完成轮次，因为"番茄钟只算专注时长"对用户未必是显然的。
- **弹窗期间继续计时**：被否决。"我决定这个任务做完了"这个判断发生在点下"完成"的那一瞬间，不是读完弹窗权衡半分钟之后；犹豫的时间不是工作时间。改为开框即暂停，选"取消"则恢复——且只恢复这个框自己停的那只表，用户早先手动暂停的保持暂停（否则用户只是瞥一眼提示就取消，计时却死了）。
- **恢复路径遇到"已做完的任务仍有计时"时结算它**：被否决。这个状态是有歧义的，结算是在猜测，而猜错的方向是重复计费。改为只清不记：既有历史数据不做迁移（修复前的坏数据是"完成了却仍在跑时"留下的，量级个位数，而迁移有销毁真实工时的风险）。同一处理也让"崩溃后隔很久重开、关闭时长被算进去"这个毛刺一并消失。

## Consequences

- 规则的作用范围只限于**被完成的那个任务自己的计时**：完成 B 不会结算正在给 A 计的时。确认框在该任务的计时运行中或已暂停时都会弹出——暂停中的计时仍挂着任务、仍占全局单例、退出时仍会被结算，放过它就等于重新造出同一种悬空状态。
- 番茄钟跑到半途允许提前结束整组，按已完成的专注时长结算，休息时长仍不计入（沿用 `settleTimer` 既有行为）。不要求先跑满一组——"任务做完了"和"计时没跑满一轮"本就是两件独立的事。
- 取消完成**不恢复**此前的计时：已结算的时间是不可变的 `TimeEntry`，恢复它意味着改写历史。任务退回"未完成 + 无计时"的干净状态，不变量只在"已做完"这一个方向上成立。反过来，重新保存一个已做完的任务（比如改标题）不会误伤正在计时的其他任务——只有"未做完 → 已做完"这一次翻转才算完成。
- 确认框挂在 `App` 顶层，状态存在 ui store 里（`completing`），冻结与恢复都是记录下来的决定而不是每次渲染重新推导的临时状态。Escape、点击遮罩、取消按钮走同一条取消路径。
- 任务侧的终态用词是"做完 / 已做完"，想法侧保留"已完成"：想法的"已完成"指"记录即完成"这一状态抵达，任务的"做完"指一条生命周期走到终点，是两个概念。`CONTEXT.md` 早已把"已做完"标注为任务语义并列入想法侧 `已完成` 的 `_Avoid_`；UI 文案（卡片徽章、已完成分组标题、今日视图折叠区、结束今天对话框、导出 Markdown 的小节标题）统一为"已做完"。作为动作的"完成"一词保留不变，它对应词汇表里的"完成任务"。
