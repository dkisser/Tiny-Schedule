# 完成任务即结束该任务的计时

任务完成（`isDone: true`）会同时结束挂在它身上的计时：先在用户点下"完成"的那一刻暂停计时，按该暂停时刻结算并清空，再把任务标记为已做完——这是一个动作，用户不需要先手动停止计时。之所以要动领域层：完成路径原先只写 `isDone`/`doneAt`，而进行中的计时是**全局单例**、独立存放在 timer store 里、仅通过 `taskId` 关联任务，两侧没有任何交叉，于是任务显示为已做完、计时却继续跑，时间被记到一个已做完的任务上。原因是结构性的而非遗漏：任务字段的任何改动都不可能影响那个单例，grep 也确认 timer 相关代码从不读 `isDone`，更没有任何 watcher 监听任务完成。要守住"已做完的任务不会被计时"，规则必须住在能同时看见任务和计时的地方。

## Considered Options

- **只改完成那一处点击处理**：被否决。"完成"是会不断长出新入口的动作（快捷键、拖拽完成、子任务、批量完成），规则写在 UI 里，下一个入口就会重犯；主进程还有一条自己的结算路径（退出时 `settleActiveTimer`），共享领域动作才能让两条路径说同一种话。
- **完成只自动暂停、不清空**：被否决。会留下一个指向已做完任务的暂停计时器，它仍占着全局单例、退出时仍会被结算——把同一个 bug 变成静态版本，比现在更难发现。
- **禁止完成（必须先停止计时）**：被否决。等于把"先结束后完成"这个两步仪式制度化，而它要解决的歧义并不存在——完成动作本身已经唯一地决定了结束时刻。
- **静默结算，不询问**：被否决。会让"完成"在无反馈的情况下改写工时，用户不知道记了多少。改为弹确认框，并显示将被记入的时长；番茄钟半途时额外提示已完成轮次，因为"番茄钟只算专注时长"对用户未必是显然的。
- **复用 `stop()` 再 `upsertTask()`**：被否决。会对同一任务连发两次写盘，两次都是 `await`，中间存在丢更新的竞态。改为共享的 `completeTask()` 纯函数，一次返回"已结算 + 已做完"的新任务，只写一次盘。
- **弹窗期间继续计时**：被否决。"我决定这个任务做完了"这个判断发生在点下"完成"的那一瞬间，不是读完弹窗权衡半分钟之后；犹豫的时间不是工作时间。改为开框即暂停，选"取消"则恢复计时（否则用户只是瞥一眼提示就取消，计时却死了）。

## Consequences

- 规则的作用范围只限于**被完成的那个任务自己的计时**：完成 B 不会结算正在给 A 计的时。确认框在该任务的计时运行中或已暂停时都会弹出——暂停中的计时仍挂着任务、仍占全局单例、退出时仍会被结算，放过它就等于重新造出同一种悬空状态。
- 番茄钟跑到半途允许提前结束整组，按已完成的专注时长结算，休息时长仍不计入（沿用 `settleTimer` 既有行为）。不要求先跑满一组——"任务做完了"和"计时没跑满一轮"本就是两件独立的事。
- 取消完成**不恢复**此前的计时：已结算的时间是不可变的 `TimeEntry`，恢复它意味着改写历史。任务退回"未完成 + 无计时"的干净状态，不变量只在"已做完"这一个方向上成立。
- 完成任务需要两次 IPC（写任务 + 清计时器），若 App 在两次之间崩溃，磁盘上会留下"任务已做完但 `activeTimer` 仍指向它"的记录。启动恢复时对此做一次性自愈：按恢复时刻结算并清空（`settleTimer` 以 `end = now` 归档，会诚实地记到重开当天），使不变量重新成立。既有历史数据不做迁移——已有的坏数据是完成了却仍在跑时留下的那段，量级个位数，而迁移有销毁真实工时的风险。
- 任务侧的终态用词是「做完 / 已做完」，想法侧保留「已完成」：想法的"已完成"指"记录即完成"这一状态抵达，任务的"做完"指一条生命周期走到终点，是两个概念。UI 文案 `TaskCard.tsx` 的「完成于」相应改为「做完于」。
